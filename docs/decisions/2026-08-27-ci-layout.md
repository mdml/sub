# CI: GitHub Actions layout

Date: 2026-08-27. Status: adopted.

## Decision

Three workflows under `.github/workflows/`: `per-commit.yml` (pushes to any branch other than `main`/`staging`, and pull requests into `staging`) runs `scripts/verify.sh`; `full.yml` (pull requests into `main`, pushes to `main`) runs `scripts/verify.sh --full` with the `CS_ACCESS_TOKEN` secret; `nightly.yml` (daily at 06:17 UTC and on demand) runs the vulnerability and freshness checks. Actions run on `ubuntu-latest` with the pinned toolchain and tool versions; a later release workflow is generated by `cargo-dist`.

## Rationale

The mental model names GitHub Actions and defines which gate runs where; this layout maps each gate to one workflow that calls the same script developers run, so CI cannot drift from local verification. The on-machine nightlies (harness compatibility against real harnesses, the mental-model audit through the `sub-mental-model` skill) need the owner's installed harnesses and user-level skill and are therefore scripts under `scripts/nightly/`, documented in `docs/nightlies/`, not workflows. Pushes to `staging` itself run no workflow because every commit reaching `staging` arrives by a pull request that already ran the per-commit gate, and rulesets forbid direct pushes. Every third-party action in the hand-written workflows is pinned to a full commit SHA with a `# vX.Y.Z` comment that Dependabot keeps current, because a public repository whose promise is code that is simple to audit should not run code that a moved tag can change.

## Revisit when

A macOS runner is needed for release builds (cargo-dist adds it), or the full gate needs a step that cannot run on a hosted runner.
