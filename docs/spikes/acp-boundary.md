# Spike: Agent Client Protocol (ACP) boundary

Executed 2026-08-26 (evening, America/New_York) by an unattended `claude` agent on branch `spike/acp-boundary`. Status: **complete**. Wall-clock: the agent's commands were timestamped 20:21–20:37 on 2026-08-26 (about 16 minutes of active work, parallel runs included); the machine clock then read 09:22 on 2026-08-27 when the PR was opened, so the elapsed time cannot be stated more precisely than "under an hour of agent activity"; no cost figure for the manager session was visible to the agent. Child costs: the claude child reported USD 0.72 for its run; codex and cursor children reported tokens only or nothing (see Gaps).

## Summary and recommendation

ACP v1 (protocol version 1, negotiated with every server tested) supplies launch, wait, observe, cancel, and resume as wire-level operations for all three harnesses, and all three ran the spike task end-to-end through the same 200-line Rust client built on the official `agent-client-protocol` 2.0.0 crate. What ACP does not carry is exactly the layer the mental model says `sub` owns: a session is bound to the agent process the client spawned, so nothing survives the manager unless a `sub`-owned process holds the connection and records state; token/cost reporting is optional, uneven across bridges, and semantically inconsistent; and native configuration (permission mode, subagent switch, which harness binary runs) reaches the child only through per-bridge `_meta`/environment side channels, with one of them not verifiably effective.

**Recommendation: wrap ACP with a small delegation layer.** Use ACP for all client↔agent communication, through the three bridges (`@agentclientprotocol/codex-acp` 1.6.2, `@agentclientprotocol/claude-agent-acp` 0.70.0, `cursor-agent acp` built into cursor-agent 2026.08.25). Put the delegated-task/attempt/evidence/result model, the supervisor process that owns the ACP connection, per-harness knowledge of transcript locations, and the native-option side channels in `sub`. Do not build native adapters: the two gaps native adapters could address (codex cost, cursor subagent switch) are not closed by the harnesses' native interfaces either. The evidence is in the Capability map, Prototype, and Gaps sections; what would change the recommendation is stated under Recommendation.

## Prototype

What ran: `spikes/acp-boundary/proto` (`acp-delegate`), a one-shot ACP client on `agent-client-protocol` 2.0.0 (`Client.builder().on_receive_notification(...).on_receive_request(...).connect_with(AcpAgent, ...)`), driven by this `claude` session as the manager. For each child it: spawned the agent process, sent `initialize` (v1), `session/new` (with optional `_meta`), and one `session/prompt` with the spike task; auto-approved permission requests (first `allow*` option); appended each `session/update` and `session/request_permission` to `events.jsonl` with a millisecond offset; and wrote `result.json` with the handle (session id + cwd), timings, stop reason, raw prompt response, counts, all `usage_update`s, and the concatenated assistant text.

Task (verbatim): "In this empty directory, create a hello-world Rust crate (binary) with one unit test. Run `cargo test` and report the full output of that command in your final message."

What it produced (the Delegate proof, child `codex`): handle `01a0409f-ada4-76c2-8c7a-68ef4d888a3b` after 979 ms; `end_turn` after 25.6 s; a crate in the empty directory; the child's final message contained the real `cargo test` output ("test tests::greeting_says_hello_world ... ok / 1 passed"). The same client, unchanged, completed the task with `claude` (17.4 s, test `greeting_is_hello_world`, USD 0.72) and `cursor-agent` (25.5 s, test `it_says_hello`). Full records: `evidence/{codex,claude,cursor}-{result.json,events.jsonl}`.

How to rerun: `spikes/acp-boundary/README.md`.

Judgement on Observe from the captured streams: the event stream is rich enough to build `sub`'s normalized log (tool calls with kind/status/locations, text, thoughts, usage) and to render live progress, but it is *not* the transcript (the vendor file is) and it contains no cumulative-cost or attempt-lifecycle facts — those are `sub`'s to add.

## Bridge maturity per harness

- **codex** — `@agentclientprotocol/codex-acp` is actively released (1.6.2 on 2026-08-20; 5 commits after the tag by 2026-08-24), maintained in the ACP GitHub org, built on codex's own `app-server` JSON-RPC (types generated from `codex app-server generate-ts`), so it tracks codex closely; it pins `@openai/codex` ^0.148.0 but `CODEX_PATH` selects the installed binary. Advertises `resume`, `list`, `close`, `delete`, `additionalDirectories`, `loadSession`, `auth.logout`, plus non-standard `_meta` extensions (steering, goals, JetBrains AIR). Mature for the beta path. Caveat: the bridge injects `projects.<cwd>.trust_level = "trusted"` and ran with zero permission requests — the child had exactly codex's native `on-request` + `workspace-write` policy, not anything the manager chose.
- **claude** — `@agentclientprotocol/claude-agent-acp` (formerly `@zed-industries/claude-code-acp`) is the most complete: `resume`/`fork`/`list`/`close`/`delete`/`loadSession`, cost in USD, native options passthrough (`_meta.claudeCode.options`, with `hooks`, `mcpServers`, `disallowedTools`, `tools` merged; `cwd`, `permissionMode`, `canUseTool`, `executable` reserved by the bridge), and an optional raw SDK-message firehose (`emitRawSDKMessages` → `_claude/sdkMessage`). Runs the Agent SDK's bundled CLI, not the user's `claude`, unless `CLAUDE_CODE_EXECUTABLE` is set; refuses to start inside a Claude Code session unless `CLAUDECODE` is unset (relevant to a `claude` manager launching a `claude` child — outside the beta path). Mature.
- **cursor-agent** — first-party, built in (`cursor-agent acp`), but the thinnest surface: no `resume` (only replaying `session/load`), no usage or cost, no known subagent switch, transcript in a private SQLite store. Works for launch/wait/observe-events/recover-by-replay. Adequate for the first release's "verify `cursor-agent`" item only with those caveats.
- **Rust SDK** — 2.0.0 is a recent rewrite (client builder + `AcpAgent` process launcher + typed v1 schema); the client path used here worked first time, but the API is young and `docs.rs` is the only documentation beyond four examples. Per-turn usage requires an `unstable_*` feature.

Comparison with existing ACP clients (as far as it informs the recommendation): Zed, JetBrains, and Neovim clients are interactive editors — they hold the agent process for the life of the UI and never need a handle to outlive the client. None of them models durable delegated work; the bridges' extensions (steering, goals, `sessionFailure`, `agentFileChangeReport`) are editor conveniences. There is no ACP client today that does what `sub` proposes, and nothing in the protocol prevents it.

## Gaps

1. **Cost and token accounting.** ACP makes usage optional. Cost (USD) arrived only from claude. Tokens: codex and claude send `usage_update` whose `used` is the *current context size* (codex uses the last turn's total; claude uses context used), not a running spend; a true per-turn spend exists only in the unstable prompt-response `usage` (present from both bridges, absent from cursor). `sub`'s "cost and tokens accumulated across attempts" must therefore be computed by `sub` from per-turn `usage` where available, be marked unknown otherwise, and price tokens itself if it wants money for codex/cursor. No native interface closes this: codex's app-server also reports tokens and rate limits only.
2. **Cross-process resume.** Works for codex and claude via `session/resume` (verified in a fresh process), and for cursor only via `session/load` replay (verified). But the ACP session dies with the agent process, and the agent process is a child of whoever spawned it: if the manager owns the connection, a manager crash kills the child mid-turn, and a running turn cannot be re-attached from another process — resume re-opens the *harness session* and starts a new turn. This matches the mental model's "recovery is resume through the harness's session" and its "each execution attempt has its own supervisor process" only if the supervisor, not the manager, owns the ACP connection. Cursor's replay-based load also means recovery cost scales with transcript length.
3. **Native-config fidelity.** ACP standardizes modes, config options, and permission prompts but nothing else. Each bridge has its own side channel: codex — `CODEX_CONFIG` (JSON merged into the thread config) and `CODEX_PATH`; claude — `_meta.claudeCode.options` on `session/new` and `CLAUDE_CODE_EXECUTABLE`; cursor — none found. The one override this spike relied on for a mental-model rule (disable codex subagents) could not be shown to take effect, and cursor offers no switch at all, so "subagents are always disabled in adapters" is not enforceable through ACP for cursor and unverified for codex. Which binary runs is also a fidelity question: both bridges default to a bundled harness build, not the one on the user's PATH.
4. **Permission authority.** Every child asked (or, for codex, was pre-trusted) and the prototype auto-approved. Nothing in ACP lets the manager pre-declare a permission policy except the bridge's mode/config options; `sub` has to decide who answers `session/request_permission` when the manager is not interactive, per mental-model decision "never grants a child more permission than the manager's params request".
5. **Result shape.** ACP has no "result" beyond the final assistant text and `stopReason`; status, summary, changed files, and artifact references are `sub`'s to derive (changed files from `edit` tool calls' `locations`, or from the bridges' non-standard file-change report).
6. **Protocol churn.** ACP v2 (draft) changes the prompt lifecycle (`session/prompt` no longer blocks to the end of the turn; completion is a `state_update`), removes `session/load` in favor of `session/resume` with replay, and removes client-side fs/terminal. The delegation layer should hide this behind `sub`'s Wait so adapters can move to v2 without changing the SDK.
7. **Bridge ownership.** Two of three transports are third-party npm packages (ACP org / Zed), fetched with `npx`, evolving weekly. `sub` would pin versions and declare them the way the mental model already says adapters declare verified harness versions.

## Recommendation

**Wrap ACP with a small delegation layer.**

Supporting evidence: one unmodified 200-line ACP client launched, waited on, observed, and (in probes) recovered sessions on all three harnesses; the protocol's stream carries everything `sub`'s events need for activity and tool-level observation; cross-process recovery exists in-protocol for all three (two by `resume`, one by `load`). Everything missing is exactly the mental model's claimed contribution — durable handle, attempt lifecycle, accumulated cost/tokens, result handoff, transcript-by-reference, permission policy — plus per-harness side channels for native options that are small, data-only (env/`_meta`), and already provided by the bridges.

Why not the alternatives: *use ACP directly* — no ACP client offers a durable handle or accumulated accounting, and the manager cannot hold the connection without dying with it. *Retain native adapters for named gaps* — the named gaps (codex cost, cursor usage and subagent switch) are not closed by the harnesses' native interfaces either, so a native adapter buys maintenance without capability. *Change the thesis* or *stop* — nothing found contradicts the thesis; the layer above ACP is thinner than feared, which favors the "small add-on beats control plane" hypothesis.

What would change it: (a) if `CODEX_CONFIG`/`_meta` side channels prove unable to enforce a rule the mental model requires (subagents off, permission ceiling) and upstream declines to add it — then a native codex/cursor adapter for that control becomes necessary; (b) if ACP v2 ships with a mandatory non-blocking prompt lifecycle and the bridges drop v1 quickly — the delegation layer still holds, but the Wait implementation must be redone; (c) if bridge maintenance stalls (the Zed-era packages went stale within five months) — `sub` would have to vendor or fork a bridge, which starts to look like a native adapter.

## Handoff

### Findings

- ACP v1 carries launch, wait, observe (events; tokens where the bridge sends them), cancel (mapped), and resume (verified cross-process for codex and claude; replay-load for cursor) for all three harnesses. All three completed the spike task through one client.
- The current bridges are `@agentclientprotocol/codex-acp` 1.6.2 and `@agentclientprotocol/claude-agent-acp` 0.70.0; the `@zed-industries/*` packages are stale. cursor-agent ships its own ACP server.
- Codex's native transcript for the handle is `~/.codex/sessions/.../rollout-*-<sessionId>.jsonl`; claude's is `~/.claude/projects/<cwd>/<sessionId>.jsonl`; cursor's is a SQLite store under `~/.cursor/acp-sessions/<sessionId>/`.
- Cost in USD came only from claude; per-turn tokens from codex and claude via an unstable ACP feature; nothing from cursor.
- Codex ran with zero permission prompts because the bridge marks the cwd trusted; claude and cursor asked for each command.

### Limitations

- Cancel was mapped from spec and bridge source, never executed.
- Recover was probed with raw JSON-RPC (not the prototype) to confirm the capability; no manager-crash scenario was simulated.
- The `CODEX_CONFIG` subagent override was sent but its effect is unverified (rollout shows multi-agent instructions still present); no cursor subagent switch exists as far as `--help` shows.
- claude ran on the bridge's bundled Agent SDK CLI, not the installed `claude` 2.1.246. This session (the manager) is itself a `claude` session, so the claude child needed `CLAUDECODE` unset.
- Single task, single run per harness; timings are one sample each.
- Global harness configuration was not changed. New files appeared under `~/.codex/sessions`, `~/.claude/projects`, and `~/.cursor/acp-sessions` as ordinary session records; they were left in place.

### Mental-model claims that may need revision

1. "`sub` supports only harnesses whose sessions can be resumed. (Verify `cursor-agent` before the first release.)" — cursor-agent has no `session/resume`; it has replaying `session/load`. Decide whether replay-based load counts as "resumable".
2. "Observe: list tasks, status, events, cost and tokens." and "cost and tokens accumulated across attempts" — cost is available only for claude; tokens are per-turn (unstable feature) for codex/claude and absent for cursor. The claim may need "where the harness reports them" or a `sub`-side pricing table.
3. "Subagents are always disabled in adapters; `sub` enforces that there is exactly one level of delegation." — enforceable for claude (`disallowedTools`), unverified for codex, not possible for cursor through any switch found. May need to become "requested where the harness offers a switch; otherwise instructed in the prompt and observed".
4. "`sub` uses ACP wherever ACP supplies the required client-agent communication. Harness-specific adapters or extensions exist only where ACP support is absent or insufficient." — supported by the evidence, with the refinement that the "extensions" are bridge side channels (`CODEX_CONFIG`, `_meta.claudeCode.options`, `CLAUDE_CODE_EXECUTABLE`, `CODEX_PATH`), not adapters.
5. "No daemon in the beta. Each execution attempt has its own supervisor process that writes state and events to `~/.sub`." — consistent with ACP only if the supervisor, not the manager, spawns the bridge and owns the connection; a manager-owned connection dies with the manager.
6. "It uses each harness's own authentication and never grants a child more permission than the manager's params request." — codex-acp pre-trusts the cwd and applies codex's native approval policy; the manager's params can lower this only through the bridge's mode/config options. Worth stating who answers `session/request_permission` when no human is present.
7. "The child's raw native stream is retained by reference: a pointer to the harness's own transcript (path and session id) where the harness writes one" — holds for all three, but ACP never reveals the path; `sub` needs per-harness layout knowledge (and cursor's is a SQLite database, not a stream).
8. "Beta scope 4. A result contains: status, summary, changed files, artifact references, and the harness session id." — ACP provides only final text, `stopReason`, and the session id; the rest is derived. Not a contradiction, but the derivation rules will be `sub`'s public semantics.

### Questions I would have asked the owner

1. Should `sub` run the harness binary on the user's PATH (`CODEX_PATH`, `CLAUDE_CODE_EXECUTABLE`) or the bridge-bundled build? The former matches "native settings stay native"; the latter is what the bridges test against.
2. Is a third-party bridge (npm, `npx`-fetched, weekly releases) acceptable in the critical path, and should `sub` pin and vendor it?
3. When the manager is an agent with no human present, who answers `session/request_permission` — auto-approve within the params' permission mode, deny, or block the attempt until the manager polls? This is a product decision.
4. Does replay-based `session/load` satisfy the "resumable" requirement for cursor-agent?
5. Is token-only accounting (no USD) acceptable for codex and cursor in the beta, or should `sub` carry a pricing table?
6. For the codex subagent switch: is "instruct in prompt + observe `subAgentActivity` tool calls" acceptable until the config override can be verified?
7. Should `sub` target ACP v1 only for the beta and defer v2 (draft) until the bridges advertise it?
