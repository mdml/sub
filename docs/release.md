# Release channels

`sub` has development, nightly, and stable channels. The mechanics and version-coupling choices are recorded in [`decisions/2026-09-02-release-channels.md`](decisions/2026-09-02-release-channels.md).

| Channel | Ref | Publication |
|:--|:--|:--|
| Development | `staging` | Development PRs are rebase-merged after the full PR gate. |
| Nightly | `main` | A dated GitHub prerelease is published after `main` moves and passes the full gate with whole-tree CodeScene. |
| Stable | `stable` | An assembled pointer based on a nightly commit plus named fixes; a stable GitHub Release and Homebrew formula are published from its stable tag. |

## Development promotion

Promotion from `staging` to `main` is a reviewed PR triggered by a proof or milestone. It must pass the full gate and be merged with a merge commit. The `main` ruleset rejects direct pushes, force-pushes, and deletion.

## Nightly releases

`.github/workflows/nightly.yml` runs daily at 06:17 UTC and can be dispatched manually. It checks the latest nightly tag and stops when that tag already points to `main`'s tip. Otherwise it runs `scripts/verify.sh --full --all`, builds `sub` and `sub-mcp` natively for the four supported targets, attests the archives, creates a workflow-owned tag such as `v0.1.0-nightly.20260902.123.1`, and publishes a GitHub prerelease with checksums.

Nightlies deliberately do not use cargo-dist's tag planner: cargo-dist 0.32 requires the tag's SemVer to equal the workspace version, while a nightly tag adds a prerelease component without changing `main`. Nightly artifacts therefore use a dedicated workflow. They are not published to Homebrew.

## Stable promotion

Dispatch `promote to stable` with a base nightly tag. Leave the cherry-pick input blank to discover commits from merged PRs carrying `stable-candidate`; discovery keeps only those commits that occur in `main` after the base and preserves their `main` order. An explicit whitespace-, comma-, or newline-separated list replaces that default.

The first dispatch should leave `confirm` false. Its summary shows the resolved base and ordered commits without changing a ref. Re-run with `confirm` true after reviewing that summary. The confirmed run:

1. Resets a local `stable` assembly to the base and applies each commit in order. Any conflict stops the run without a remote change.
2. Derives the next 0.x version from Conventional Commits since the last stable tag: breaking changes and `feat` produce a minor bump; all other releases produce a patch bump. `version_override` accepts an exact, advancing `0.x.y` version.
3. Cuts `CHANGELOG.md`, refreshes workspace versions, and runs the full gate with whole-tree CodeScene before committing release preparation.
4. Proves that the release-prep commit cherry-picks cleanly onto current `staging`. A conflict stops the run without a remote change.
5. Atomically pushes `stable`, the stable tag, and a `chore/stable-release-vX.Y.Z` reconciliation branch. It opens a small PR from that branch into `staging` and explicitly dispatches its full gate.
6. Dispatches the generated cargo-dist release workflow for the new tag. cargo-dist builds, attests, and publishes the stable GitHub Release and Homebrew formula.

The base must resolve to a nightly tag on `main`. `allow_untagged_base` is an explicit emergency override and is called out in the run summary. No human creates a release tag.

## Initial setup and rulesets

Before the first release, create `mdml/homebrew-tap` and configure `HOMEBREW_TAP_TOKEN`. The owner must also create the `stable` branch and release-tag rulesets with the commands in the release-channel decision record. Apply the rulesets before the first confirmed promotion; do not create `stable` manually. The workflow's GitHub Actions bypass then creates the protected branch.

No `main` ruleset change is required: the existing rule already requires the `verify-full` context, allows only merge-commit PRs, and blocks deletion and non-fast-forward updates.

## Distribution

`cargo-dist` 0.32.0 is configured in `dist-workspace.toml`. `.github/workflows/release.yml` is generated by `dist generate` and must never be edited by hand. Regenerate it after changing cargo-dist configuration.

- Homebrew receives stable formulas in `mdml/homebrew-tap` and never receives prereleases.
- `mise use ubi:mdml/sub` installs from GitHub Releases; no additional publishing step is needed.
- `cargo binstall` consumes cargo-dist's stable archive names and checksums.
